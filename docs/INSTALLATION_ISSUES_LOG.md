# Greia OS Installation & Boot Issues Log

**Status:** accepted engineering record  
**Date:** 2026-08-18  
**Audience:** platform developers, install/boot engineers, reviewers, agents  
**Scope:** Every issue encountered while getting the Greia installer to run on a legacy-x86/i686 Acer Aspire One (2010-era, Intel Atom N270, SATA, SynPS/2 Synaptics touchpad, Wi-Fi only), and the fixes applied. These are genuine bugs and design flaws found by physical hardware testing; each is listed with its root cause, the fix, and the commit.

---

## 1. Installer "BOOT FAILED" after mounting/unmounting the live medium

**Symptom:** Booting the Greia live installer from removable media printed
`mounted filesystem with ordered data mode. Quota mode: none.` then
`unmounted filesystem`, followed by the live-boot panic
`BOOT FAILED` / "Unable to find a medium containing a live file system".

**Root cause:** `live-boot`'s `matches_uuid()` requires the initramfs
`/conf/uuid.conf` to match a `.disk/live-uuid` marker on the live medium. The
initrd carries `greia.live_media_id`; without the `.disk/live-uuid` file on the
USB/SD the medium is probed, mounted, checked, and rejected (the "mounted /
unmounted filesystem" messages), then boot fails.

**Fix:** Ensure the removable medium carries `.disk/live-uuid` containing the
same value as the initramfs `/conf/uuid.conf`. The official installer image does
this; hand-assembled media (the syslinux USB) must include it.

**Related:** The Acer's BIOS cannot boot the SD reader at all, and would not
execute the iamaKey USB stick's GRUB MBR. A **syslinux** bootloader (the same
mechanism antiX uses) plus a clean FAT32 active partition was required for USB
boot.

## 2. Acer boots installed system to a grey screen, then reboots (boot loop)

**Symptom:** After a completed install, GRUB loaded the "Greia OS" entry, the
screen went grey, and after a few seconds the machine rebooted endlessly.

**Root cause:** The installed system's initramfs (regenerated by
`update-initramfs` during install) was **missing the SATA/AHCI storage
drivers** (`ahci.ko`, `libata.ko`, `sd_mod.ko`). The initramfs-tools config that
forces `MODULES=most` (`/etc/initramfs-tools/conf.d/greia-hardware`) was **not
present in the installed target**, so initramfs-tools fell back to
dependency-mode and excluded the drivers because the chroot build had no Acer
hardware to probe. Without `/dev/sda`, root could not mount, the kernel panicked,
and `panic=5 console=null` silently hid the panic and auto-rebooted.

**Fix:**
- Restore `MODULES=most` and `/etc/initramfs-tools/modules` with
  `ahci`, `libata`, `sd_mod` in the installed target.
- Rebuild the initramfs (`update-initramfs -u -k all`).
- The installer should fail loudly if the regenerated initramfs lacks the
  storage drivers (defensive verification added in `de6299e`).

## 3. Installer stalls mid-install ("Adding support for this computer")

**Symptom:** During the hardware-support step, the installer appeared frozen;
`apt-get` was found in state `T` (stopped) at `do_signal_stop` and could not be
resumed.

**Root cause:** The live installer service was launched with
`StandardInput=tty` and `TTYPath=/dev/tty1`. xinit takes over tty1 as the
foreground process group, making the installer's children a **background process
group whose stdin is still the terminal**. The first child to read stdin
(apt-get) was sent **SIGTTIN**, freezing it permanently. Same class of failure
hit `grub-mkpasswd-pbkdf2` later.

**Fix:**
- `greia-installer.service` and `greia-launcher.service` now use
  `StandardInput=null` instead of `StandardInput=tty` (`665909d`).
- `SubprocessRunner` in `engine.py` and `disk.py` now pass
  `stdin=subprocess.DEVNULL` so no child inherits the VT (`9654d01`).

## 4. "installation payload not found"

**Symptom:** The live installer started (after the `.disk/live-uuid` fix) but
reported "installation payload not found".

**Root cause:** The hand-built syslinux USB contained the live
`vmlinuz`/`initrd.img`/`filesystem.squashfs` but **not the `payload/`
directory** with `pip-rootfs.squashfs`, its `.sha256`, and
`target-image-profile.json`. The installer expects these on the medium.

**Fix:** Place the full `payload/` payload set on the medium, matching
`/etc/greia-os/expected-payload.sha256`. The official build does this; custom
media must too.

---

## 5. Installed system boots but SSH fails to start

**Symptom:** `ssh.service` failed; no SSH access to the installed system.

**Root cause:** The installer's `_personalize_target` deliberately removes SSH
host keys so they are regenerated on first boot. On this image the regeneration
did not happen, so sshd could not start.

**Fix:** Generate SSH host keys in the installed target
(`dpkg-reconfigure openssh-server` or `ssh-keygen -A`) after install. The
installed sshd config (dev profile) allows `greia`/`root` with password auth.

## 6. greia-launcher.service fails with status 226/NAMESPACE

**Symptom:** `greia-launcher.service` failed at
`ExecStartPre=/usr/local/lib/greia-os/prepare-launcher-vt` with
`Failed at step NAMESPACE ... /run/greia-os: No such file or directory`.

**Root cause:** The service uses a sandbox with `ReadWritePaths=/run/greia-os`
and `ProtectSystem=strict`. systemd sets up the mount namespace **before**
`ExecStartPre` runs, and the namespace setup requires `/run/greia-os` to already
exist. On a fresh boot (tmpfs `/run`), it did not.

**Fix:** Add `RuntimeDirectory=greia-os` to the service so systemd creates
`/run/greia-os` before the namespace is set up.

## 7. Xorg refuses to start: "Only console users are allowed to run the X server"

**Symptom:** The launcher's Xorg never started; the journal showed
`/usr/lib/xorg/Xorg.wrap: Only console users are allowed to run the X server`,
and `[Xorg] <defunct>` zombies appeared.

**Root cause:** `Xwrapper.config` had `allowed_users=console`. The launcher
service runs under systemd with a PAM session that is **not** registered with
logind as a physical-console session, so Xorg.wrap rejected it.

**Fix:** For the appliance, set `allowed_users=anybody` and
`needs_root_rights=yes` in `/etc/X11/Xwrapper.config`.

---

## 8. Xorg blocked by the launcher service sandbox (grey screen, stale Xorg log)

**Symptom:** Even after the wrapper fix, Xorg produced no log and the launcher
kept restarting. The fresh Xorg log was never written.

**Root cause:** The launcher service's sandbox (`ProtectSystem=strict`,
`PrivateTmp=yes`, `ProtectHome=yes`) prevented Xorg from opening its VT, input
devices, DRM, and from writing `/var/log/Xorg.0.log`. A display server cannot
run under that sandbox.

**Fix:** Remove the heavy systemd sandbox from `greia-launcher.service`
(display-manager-style service running Xorg as root). The launcher UI then
starts and stays up.

## 9. Frozen mouse / touchpad in the launcher

**Symptom:** The launcher UI showed, the pointer rendered, but could not move.
`Xorg.0.log` showed
`libinput: SynPS/2 Synaptics TouchPad: Failed to create a device for /dev/input/mouse0`.

**Root cause:** The touchpad is exposed twice: once as `event6` (a real libinput
device) and once as the legacy `/dev/input/mouse0`. The `90-greia-input-defaults`
`MatchIsPointer` class matched `mouse0` and tried libinput on it, which failed
and broke the device.

**Fix:** Add an InputClass that ignores `/dev/input/mouse*`
(`Option "Ignore" "true"`) so only the real `event*` touchpad device is used.

---

## 10. Activities fail to launch: bwrap sandbox errors

**Symptom:** Clicking an Activity did nothing (silent return to the launcher).
Instrumentation showed `ActivityExitReason.CRASH` and stderr:
`bwrap: Can't find source path .../activities/org.greia.painting: Permission denied`.

**Root cause (three parts):**
1. The sandbox bound the storage/event socket roots and activity data to
   `/run/...` targets that did not exist under the read-only `--ro-bind / /`
   root, so bwrap could not create the mount points.
2. `/run` is read-only in the sandbox; bind targets under it cannot be created.
3. `--unshare-user`/`--disable-userns` remapped root into a user namespace that
   loses access to `greiakid:pipprofiles` group-owned profile directories, so
   bwrap could not traverse the source path.

**Fix (`51c7592`):**
- Add `--dir` before the storage/event `--ro-bind` targets.
- Add `--tmpfs /run` so mount points under `/run` can be created.
- Remove `--unshare-user`/`--disable-userns`; PID/network/UTS isolation and a
  read-only root remain.
- Ensure the profile directory traversal chain is accessible (o+x on parent
  dirs) to the sandbox process.

## 11. Arrow/Enter keyboard navigation dead in the kiosk launcher

**Symptom:** Pointer worked, but arrow keys and Enter did nothing.

**Root cause:** The launcher runs Xorg with **no window manager**. Without a
WM, X sends keyboard events only to the input-focused window; there is none
(`XGetInputFocus` returned 0x0), so keyboard events went nowhere.

**Fix (`b1c9669`):** After creating the SDL window, set X input focus to it
via `XSetInputFocus` (ctypes call in `_set_x11_input_focus`). Arrow/Enter
navigation then works.

---

## 12. Activity launch felt frozen; feedback was a floating label

**Symptom:** Between clicking an activity and it appearing, the screen froze;
the "Starting…" text had no background and was lost over the UI.

**Fix (`b1c9669`):** Draw an immediate full-screen "Starting…" overlay with a
pulsing spinner and a solid panel that visually blocks interaction until the
activity is ready.
